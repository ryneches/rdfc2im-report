but its subject lines are terse and the first commit has no description at all. This file restates
the history in plain terms: what each commit changed (as a rule, not a story), how the problem was

  The report-pointer commits (`94a7b91` onward) are left out.
- **Writing rule.** Approach describes the end product, not the history. A rule that a later
  commit replaced is marked *superseded by `<hash>`* in the "feeds" column; it goes to Discussion
  only if it shows a conceptual point, and is otherwise left to this history.

`make all` runs allow, translate, tsv, items, project, check and docs in order (fetch only with
`FETCH=1`). Each Makefile target is one `python3 -m rdfc2im <command>` call. The only dependencies
are PyYAML and lxml.

### Step 1: models

**The InterMine model is limited to the mine's own sources.** `allow` reads HumanMine's
`project.xml` and lists the name and type of each `<source>`. `model.py` then loads `core.xml` and
`genomic_additions.xml` always, and a source's `*_additions.xml` and `*_keys.properties` only if its
directory is on that list. `curation/extra_allow.txt` adds directories that are not in
`project.xml` (only `/uberon/`, so that the Uberon class `AnatomyTerm` exists). The model keeps
classes, inheritance, fields (attribute, reference or collection, with reverse references),
integration keys, and a `term` URI index over classes and fields. OBO term URIs are normalized
(`SO:0000704` and `SO_0000704` are the same term). The live HumanMine model
(`humanmine_model.xml`, from humanmine.org) is loaded separately, for validation.

`key_attribute(cls)` picks the one attribute that identifies an object of a class in a table row.
It prefers a single-field key, in this order: `primaryIdentifier`, `identifier`,
`primaryAccession`, `taxonId`, `pubMedId`, `name`, `value`, `symbol`. A class with no key falls back
to a common identifier attribute. This one choice is used everywhere later: to mark required
columns, to key items, and to write draft keys.

**The rdf-config model is read as a tree of subjects.** `rdfconfig.py` parses rdf-config's
`model.yaml` grammar: subjects with example IRIs and `a` types, predicates with cardinality
suffixes (`?`, `*`, `+`, `{n,m}`), object variables with example values, references to other
subjects by name, and inline blank nodes (`[]`). An object is a literal, an IRI, a link to another
subject, or an inline blank node. `prefix.yaml` and `endpoint.yaml` give the prefixes, the SPARQL
endpoint and the graph names.

### Step 2: map

**Traversal.** `mapping.py` starts at each root subject (from the curator, else `roots` in
`sources.yaml`, else the first subject in `model.yaml`) and walks the subject graph breadth-first,
so each subject is placed on its shortest path from the root. A subject reachable by two paths
keeps the first one (with a message). Subjects that cannot be reached are recorded with
`role=skip`. Each (subject, predicate, object variable) becomes one mapping row. Each non-blank
subject also gets a `-self-` row for its own IRI, because some identifiers exist only in the IRI
(UniProt accessions, GO ids).

**Subject binding** (which InterMine class a subject becomes), first match wins:

1. a source-specific entry in `knowledge.yaml`, by subject name;
2. an `rdf:type` of the subject that equals the `term` URI of a model class;
3. a generic `knowledge.yaml` entry, by `rdf:type`;
4. a subject name that equals a model class name;
5. an inline blank node with no class of its own takes its parent's class (it is flattened onto
   the parent);
6. otherwise `todo`.

**Predicate binding** (which field a row writes), first match wins:

1. a source-specific `knowledge.yaml` entry (usually with evidence from the stock Java converter);
2. the predicate URI equals the `term` of a field on the bound class or an ancestor;
3. a generic `knowledge.yaml` entry;
4. the predicate URI is the `term` of a field on an unrelated class, and the bound class has a field
   of the same name (a `guess`);
5. the variable or predicate local name equals an attribute name;
6. otherwise `todo`.

A knowledge entry may name a field on a different class (for example `Synonym.value` from a Gene
subject). The row then records `via`, the reference or collection that connects the two classes
(`Gene.synonyms`). A row that lands on a reference or collection is rewritten to the key attribute
of the target class, with the reference as `via`. So every mapped column is an attribute, and every
link between objects is a `via`. A mapped field that is not in the model is marked `new-field`, and
`translate` writes it to the source's `additions.xml`.

**Row status** is the switch that decides what loads:

| status | meaning | loads |
|---|---|---|
| `sure` | backed by evidence: a term URI match, a stock Java converter, a `.properties` file, an exact name | yes |
| `guess` | a proposal from general knowledge | yes (unless `--no-guess`) |
| `human` | set or changed by the curator | yes |
| `todo` | undecided | no |
| `drop` | deliberately not loaded | no |
| `link` | structural (the object is another subject) | no data of its own |

Each row also records its `basis` (for example `term`, `name`, `java:NcbiGeneConverter`,
`knowledge`, `spec-section-8`). In the snapshot's `knowledge.yaml`, 122 entries have basis
`knowledge`, 15 have `term`, and 89 cite a stock converter (`java:...`, alone or combined), out
of 243 entries with a basis.

**Tables.** A table is one SPARQL query and one TSV file. A row goes to `main`, unless it is under a
multi-valued predicate (`*`, `+`, `{n,m}`) that creates another object (a synonym, a
cross-reference, a citation). Such a row goes to its own table named after that predicate
(`main_<variable>`). Each table holds the root key plus its own columns, so two multi-valued
predicates never multiply each other's rows. A multi-valued plain attribute of the root stays in
`main`. A `knowledge.yaml` entry can force a table.

**Pruning.** Everything under a subject with `role=skip`, or under a link row whose status is
`todo` or `drop`, is kept in the mapping file but gets `table=drop`, so it generates no query. In
the snapshot this pruned 399 UniProt rows and 371 Reactome rows.

**Constants.** A knowledge entry can add a constant column to its table (`const`), and
`sources.yaml` can add one to every table of a source (`consts`, for example
`Organism.taxonId: 9606`). Constants are written into the TSV at the cleaning step.

**Curation files.** Each source has two files that the curator edits:

- `mapping_subjects.tsv`: one row per subject, with `im_class`, `role` (`root`, `node`, `skip`),
  `status` and `note` editable.
- `mapping_predicates.sssom.tsv`: one row per (subject, predicate, column), in SSSOM layout. The
  standard columns are `subject_id` (the predicate IRI), `object_id` (`intermine:Class.field`),
  `predicate_id` (`skos:exactMatch` for sure/human, `skos:closeMatch` for guess, `sssom:NoMapping`
  otherwise), `mapping_justification` (semapv: manual curation for `human`, lexical matching for a
  name match, mapping chaining for a term URI match, unspecified otherwise) and `confidence` (1.0,
  0.5 or empty). rdfc2im's own columns (`ext_status`, `ext_table`, `ext_transform`, `ext_filter`,
  `ext_value`, `ext_required`, `ext_via`, ...) are declared as SSSOM extension slots in the YAML
  header.

**Three-way merge.** `translate` regenerates both files on every run. It keeps a hidden snapshot of
its last automatic output (`.mapping_*.base.*`). For each editable cell, a value the curator
changed (the file on disk differs from the base) is kept, and an untouched value takes the fresh
output. A row whose cells were edited but whose status was not is marked `human`. A row whose key
has left the fresh output is kept and marked `STALE`. So `make all` is safe on a curated workspace,
and the mapping files plus their base snapshots are the whole curation state.

### Step 3: extract

**SPARQL generation** (`sparql.py`): one query per table. The query walks from the root to each
column along the subject tree. Only `required=yes` rows are required triple patterns. By default
that is only the key attribute of the root class, so the root's key is always required. Every other
pattern, and every sub-tree with no required row, is `OPTIONAL`. A `value` becomes `VALUES ?x { ... }`
for an IRI or CURIE, or `FILTER(STR(?x) = "...")` for a quoted literal (how the query is limited to
taxon 9606, for example). Each query has an `a <type>` triple on the root (`rdfs:Resource` and
`owl:Thing` are skipped), `SELECT DISTINCT`, `FROM` the graphs in `endpoint.yaml`, only the
prefixes it uses, and a header comment naming the endpoint. A table that would hold only key columns
is not generated. The same queries are also written as `humanmine*` blocks appended to a copy of
the source's `sparql.yaml`, so they can be checked against rdf-config's own generator.

This differs on purpose from rdf-config's own generator, which makes every predicate without `?`
or `*` required. rdfc2im's rule (only the identifier is required) replaces the specification's
"optionalize_model" step.

**Fetch** (`fetch.py`): each query is sent to the endpoint named in its header, by POST and then GET,
asking for SPARQL JSON, then TSV, then CSV. Every format is converted to W3C SPARQL TSV in `raw/`.
With paging on (default 5,000 rows), the query gets `ORDER BY` its first variable and
`LIMIT n OFFSET k` until a short page returns. A failed page after the first is reported as
"partial". A redirected POST is sent again as a GET with the query in the URL. A query that returns
no rows is flagged. Existing files are kept unless `FORCE=1`. The default `LIMIT` is 20 rows, for
checking queries before a full extract.

**Cleaning** (`tsv.py`): the raw terms (`<iri>`, `"literal"`, `"v"^^<datatype>`, `"v"@lang`) become
plain values. Per column, a `filter` (`regex`, `nonempty`, `equals`) runs first, then a chain of
`transform` steps: `iri_localname`, `prefix`, `strip_prefix`, `replace`, `regex` (keeps a group),
`split` (one value becomes several rows), `lower`, `upper`, `int`. A required column that fails its
filter drops the row. Any other column that fails is blanked. Constants are appended. Rows with no
data and duplicate rows are removed. The header is `Class.field` per column.

### Step 4: load

**Output format.** The snapshot's STATUS.md, finding 1, explains why v0.2 writes Items XML and not
delimited files. InterMine's delimited loader links two objects only when the referenced type is
literally a class in the row. For example, `Synonym.subject` has type `BioEntity`, so it never
links to a Gene. The loader also links every pair of objects that occur in the same row, allows one
object per class per row, cannot express links within one class (`OntologyTerm.parents`), and
de-duplicates objects by all their values. In Items XML every attribute, reference and collection is
explicit, so a link exists exactly where the mapping has a `via`.

**Items** (`items.py`): every row of every table is split into objects by (class, `via`): the root
object, plus one object for each linked class. An object's identity is (class, key attribute,
value). A class with no key attribute value is identified by a hash of all its values. So the same
Gene met in ten tables becomes one `<item>`, and its attributes accumulate. When two rows give one
field different values, the first value is kept and the conflict is logged. Links follow `via`, and
the reverse reference is set too (`Gene.synonyms` also sets `Synonym.subject`). A column with no
`via` links from the table root through the first reference or collection whose type fits. The
table root is the class of the first required column. A link within one class
(`OntologyTerm.parents`) is an ordinary row. Each source gets one DataSource and one DataSet, and
every item that has `dataSets` or `dataSet` is attached to it.

**Loader.** `humanmine-items/` is InterMine's stock items-XML source under its own type name, with
no Java. Having its own type lets the generated keys and additions travel in the source's jar. In
the snapshot it uses `have.file.xml.tgt` (the plain items-XML loader). The large-file loader is
mentioned as an option.

**Mine configuration** (`project.py`):

- `project.xml`: HumanMine's own, with one `humanmine-<source>` source per rdf-config source,
  inserted where the first replaced stock source was. The stock sources that a source `replaces`
  (from `sources.yaml`) are removed and saved to `replaced_sources.xml`.
- `humanmine-items_keys.properties`: for every class the mappings use (plus DataSet and DataSource),
  the keys from the model's keys files, following inheritance. A class with no key gets a `DRAFT`
  key on its `key_attribute`, marked for review.
- `humanmine-items_additions.xml`: the union of every source's `additions.xml` and
  `curation/extensions_additions.xml`. That file holds the model extensions the specification
  approved: `Gene.typeOfGene`, `Pathway.description`/`organism`/`reactions`, a new
  `PathwayReaction` class, `Allele.reviewStatus`/`submissionCount`, `MeshTerm.identifier` and
  `GWASResult.mappedTraitUri`.
- `genomic_priorities.properties`: a draft that lists each field written by more than one rdfc2im
  source. Merging it with HumanMine's own priorities is left to the curator.
- `links_report.txt`: per source, the classes, the links and their reverse references.

**Check**: hard problems are a class or field that is in neither the model nor the additions, a
column mapped to a reference or collection, a `via` that is not a reference or collection or whose
range does not fit the column's class, an unknown class in an items file, and a dangling `ref_id`.
Notes (soft problems) are a draft key on a root class, a class with no key (its items never merge),
and a replaced stock source that is still active.
